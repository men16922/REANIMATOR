# REANIMATOR 재기획

> **고전 게임을 되살리고, 규칙을 바꿔 나만의 게임으로 만든다.**
> Kiroween 2026 · Resurrection · 2026-11-14 · Carbon 독립 리뷰 반영 v2.1

## 1. 이번에 만들 것

**REANIMATOR는 고전 게임 한 편을 복원하고, 한 가지 새 규칙으로 재해석하는 브라우저 게임이다.**
첫 작품은 Hunt the Wumpus다. 플레이어는 위험 신호를 읽고 괴물을 추적한다. 주 사용자는 설치 없이 짧은 추리 게임을 즐기는 플레이어다. 복원 비교는 플레이어와 심사위원에게 무엇을 보존하고 바꿨는지 보여주는 제작 근거다. 범용 개발 도구 판매를 이번 제품의 가치로 주장하지 않는다.

| 결정 | 추천안 |
|---|---|
| 출품물 | 새 REANIMATOR 프로젝트. 기존 BLACKOUT 게임의 개명·재출품은 하지 않는다 |
| 기준 게임 | ESR Wumpus 1.12. 소스·라이선스·실행 확인을 통과해야 확정 |
| 플레이 | Classic 복원 → Blackout 변형 → 변경 이유 확인 |
| 내 버전의 핵심 | 불붙인 화살로 방을 확인한다. 정보에 화살을 쓸지, 사냥에 남길지 선택한다 |
| 기존 프로젝트 활용 | BLACKOUT의 전력·정보·위험 설계 경험, 순수 규칙 엔진과 패키지 검증 방식 |
| REA 활용 | 허가된 reference 바이너리 분석, 근거 연결. 제품을 자동 제작하는 만능 도구로 설명하지 않는다 |
| 구현 환경 | TypeScript 규칙 엔진 + React/Vite + SVG/CSS 기반 동굴 노드·통로 표현 |
| 주 목표 | Best Resurrection 경쟁력. 종합상·Best Demo를 함께 고려 |
| 상품화 | 우선 작은 유료 인디 게임. 복원 도구 판매는 후속 고객 검증 뒤 판단 |

**이번 작업은 계획과 독립 리뷰다. 게임 구현·REA 실행·Kiro 사용·테스트·출품은 아직 완료하지 않았다.**

공식 조건의 상세 확인은 [규정 메모](../reference/KIROWEEN_2026_REQUIREMENTS.md)에 있다.

## 2. 왜 이렇게 바꾸는가

기존 명세는 원본 기록과 새 엔진을 비교하는 기술 설계가 탄탄하다. 반면 사용자가 무엇을 즐기고, 왜 이 제품을 다시 찾는지 약하다. 검증 화면만 잘 만들어서는 기억에 남는 게임이나 판매할 제품이 되기 어렵다.

| 선택지 | 얻는 것 | 이번에 선택하지 않는 이유 |
|---|---|---|
| BLACKOUT 전체를 개편 | 이미 있는 3D 전투·자산·콘텐츠 | 신규 프로젝트 설명이 어렵고, 대규모 게임의 미술·오디오 마감 비용이 크다 |
| Wumpus 포팅·검증만 | 가장 작은 실행 범위 | 기술 데모에 머물 가능성이 있고 나만의 게임이라는 목표가 약하다 |
| **Wumpus 복원 + Blackout 규칙 변형** | 복원 증거, 신규 플레이, 짧은 시연 | 추천. 두 모드를 같은 작은 엔진 위에 구축한다 |
| 임의 게임 업로드·자동 리메이크 | 큰 제품 비전 | 권리·분석·실행 환경·평가 범위가 대회 기간을 넘는다 |

BLACKOUT 문서에는 시스템 수와 자동 검사 증가가 시각·청취 품질로 바로 이어지지 않았던 기록이 있다. 이번에는 **첫 30초의 플레이와 한 장면의 완성도**를 먼저 확인한다. 테스트 수를 재미의 증거로 사용하지 않는다.

## 3. 심사위원이 경험할 90초

이 흐름은 짧은 안내 시나리오의 목표다. 자유 플레이의 모든 판이 90초 안에 끝난다는 뜻은 아니다. 정해진 시나리오를 쓰면 화면에 표시한다.

1. **0–15초: Play.** 설명을 길게 읽지 않고 빛이 끊긴 동굴에 들어간다. 인접 방의 위험 신호와 이동 선택지가 보인다.
2. **15–40초: 선택.** 이동하거나, 화살 경로를 정하거나, Blackout 모드에서는 조명을 사용한다. 단서 획득과 위험의 대가를 체감한다.
3. **40–60초: 결과.** 승리·패배 원인이 한 문장으로 설명된다. 같은 조건으로 다시 시작할 수 있다.
4. **60–90초: What changed?** 복원 규칙과 새 규칙 한 개를 확인한다. 개발자가 원하면 기록 비교를 열어 첫 차이까지 따라간다.

첫 화면의 주 버튼은 **Play Blackout**, 보조 버튼은 **Play Classic**이다. 검증 도구는 **How it was revived**로 들어간다. 첫 화면에 소스 해시·테스트 표·MCP 로그를 펼치지 않는다.

### Blackout 규칙: 불붙인 화살

**같은 화살을 정보와 공격에 나눠 써야 한다.** 원본의 모호한 위험 경고는 유지하고, 조명은 선택한 방의 정확한 내용을 알려준다.

| 항목 | 규칙 |
|---|---|
| 대상 | 현재 방에서 실제 통로로 연결된 방 하나 |
| 조건 | 화살이 2개 이상이고, 이번 원정의 조명 사용이 3회 미만일 때 |
| 비용 | 화살 1개와 조명 사용 횟수 1회. 공격용 마지막 화살은 남긴다 |
| 효과 | 선택한 방의 괴물·구덩이·박쥐 유무를 **현재 시점의 관찰**로 표시 |
| 즉시 상태 | 플레이어·괴물·위험 방 위치는 바뀌지 않으며 난수를 소비하지 않음 |
| 이후 | 정상 이동·사격 규칙으로 계속한다. 괴물이 움직일 수 있는 행동 후 과거 관찰을 현재 안전 보장으로 표시하지 않음 |
| 실패 입력 | 인접하지 않은 방, 비용 부족, 종료 상태는 거부하고 상태·난수를 변경하지 않음 |

한 원정 3–5분, 조명 최대 3회는 플레이 검증 전 가설이다. 원본 조사에서 공간·탄약 전제가 다르면 P0에서 이 계약을 먼저 개정한다. 영구 성장·인벤토리·직업·제작·보스는 넣지 않는다.

지도는 **현재 방과 실제 연결 통로가 분명한 노드 뷰**로 만든다. 화면상 거리가 이동 가능 여부처럼 보이지 않게 하고, 숨은 위험은 일반 화면에서 노출하지 않는다.

### 복원과 변형의 검증 경계

1. **Classic:** 고정 환경 원본에서 수집한 raw 난수 테이프와 논리 입력으로 전체 기록을 비교한다. seed만 같은 비교는 허용하지 않는다.
2. **조명 0회:** 같은 시작 조건·입력·테이프의 Blackout 실행이 Classic의 비교 대상 상태·이벤트와 일치해야 한다.
3. **첫 조명 이후:** 화살과 관찰 상태가 달라졌으므로 기존 원본 기록과 전체 세션 동등성을 더 이상 주장하지 않는다. 화면은 `Variant contract`로 전환한다.
4. **변형 검증:** 조명 직전/직후에서 화살 -1·사용 횟수 +1·관찰 갱신만 허용한다. 위치·위험 배치·난수 소비 불변을 확인한다. 비용 경계, 잘못된 입력, 이후 이동·사격의 회귀 사례를 별도 작성한다.
5. **검증의 한계:** 두 모드가 공통 함수를 공유한다는 사실은 독립 원본 검증이 아니다. 분기 이후는 요구사항 기반 회귀 검증이며 `원본 동등성 PASS`에 합산하지 않는다. 미래에 독립 C 상태 주입 오라클을 만들려면 계측 타당성부터 별도 검증한다.

| `/Desktop/AI/rea` | REA 6.9.0, MIT. 고정 revision은 출처 등록부 참조 | 고정 revision의 분석 도구로 사용. 수정·전체 vendoring은 하지 않음 |
| Wumpus | 공개 reference 후보 | 원본 고지 유지, 실제 배포본 확인 후 소스·계측 패치 분리 |

대회 이전 자산은 `docs/PREEXISTING_WORK.md`에 출처·날짜·라이선스·사용 범위·신규 작업을 기록한다. 새 폴더를 만들었다는 사실만으로 신규성을 주장하지 않는다. **신규 기여는 브라우저 복원 엔진, 비교 경험, 변경 규칙 계약, 새 플레이 화면**이다.

상용 고전 게임의 바이너리·그림·음악·대사·수치 테이블은 이번 공개물에 넣지 않는다. REA의 MIT 라이선스는 분석 대상 게임의 권리를 부여하지 않는다. 상용 IP 기반 판매는 권리 허락을 확보하는 별도 트랙이며 이번 출시의 전제가 아니다.

## 5. 기술 구조와 REA의 구체적 역할

```text
허가된 Wumpus 소스 → 고정 환경에서 원본 실행 → reference 기록
         │                                      │
         └→ 자체 빌드 바이너리 → REA 분석 근거     │
                                  ↓              ↓
                       Kiro 요구사항·설계 → Classic 엔진 → 비교기
                                               │
                                     Blackout 규칙 모듈
                                               │
                                    브라우저 플레이·설명
```

원본 소스가 있으므로 일부러 소스를 감추고 “잃어버린 코드를 복원했다”고 연출하지 않는다. 분석자는 이미 원본 관련 정보를 접했으므로 이번 조사를 블라인드 평가로 부르지 않는다. **소스가 공개된 고전 게임으로 분석→규칙 추출→재구현→검증의 방법을 증명**한다.

REA는 아래 질문 중 **소스 열람만으로 부족한 실제 빌드·실행 확인에 도움이 되는 것**을 선택한다. 단순히 소스에서 읽은 답을 다시 보여주는 결과라면 주 시연에서 제외한다.

| 질문 | 근거 | 완료 기준 |
|---|---|---|
| 어떤 함수가 이동·사격·종료를 처리하는가? | 실제 바이너리 분석 결과와 소스 대조 | 후보와 확인된 매핑을 구별한 조사 기록 |
| 난수는 언제 소비되는가? | 정적 호출 위치 + 실제 원본/계측 실행 | 호출 순서와 미관찰 경로를 명시 |
| 새 규칙이 어떤 경계를 바꾸는가? | 원본 행동 명세와 변경 규칙 계약 | 기존 규칙/신규 규칙/미확인 항목의 구별 |

REA provider 연결과 지원 도구는 **아직 실행 검증하지 않았다**. 첫 조사에 최대 2 agent-hours를 배정한다. 막히면 원인과 부분 근거를 남기고 소스·직접 실행으로 reference 작업을 계속한다. REA를 사용하지 못했다면 제출물에서 실제 REA 활용을 주장하지 않는다.

전체 난수·계측·비교 계약은 [기술 계약](../reference/VERIFICATION_CONTRACT.md)에 둔다. 공개 앱은 정적 빌드와 사전 기록으로 동작한다. 심사자가 REA·C 컴파일러·Kiro를 설치할 필요가 없다.

## 6. 수상 전략: 주장마다 장면 하나

공식 기준은 Impact·Implementation·Design·Innovation·Presentation 각각 20%다. 아래는 자체 전략이며 수상 예측 점수가 아니다.

| 기준 | 보여줄 증거 | 약점을 줄이는 작업 |
|---|---|---|
| Impact | 플레이어가 정보와 탄약의 선택을 이해하고 다시 플레이하는 경험 | 11/29–30에 플레이어 3명 관찰: 비용 이해·막힌 지점·재도전 의향 기록 |
| Implementation | Kiro가 원본 조사 명세→구현→실패 수정에 기여한 실제 기록 | 설정 파일 존재만으로 사용 완료 처리하지 않음 |
| Design | 설치·로그인 없이 시작부터 결과까지 플레이 | 30초 안에 첫 선택; 1440px·390px·키보드 흐름 확인 |
| Innovation | 의도한 변화와 실수로 바뀐 규칙을 분리 | 단순 리스킨과 다른 점을 한 장면으로 표현 |
| Presentation | 원본→현대 플레이→새 규칙→검증의 2분 40초 시연 | 실제 빌드만 촬영; 사전 기록과 live 실행을 명시 |

2025 공식 수상작 갤러리에는 InteractionKit, Faxi, ELIZA EXHUMED 등이 있다. 각각 상호작용·구체적 이용자 문제·옛/새 경험 비교를 전면에 내세운다. 이는 참고 패턴이지 심사 인과관계나 올해 수상의 보장은 아니다. [공식 갤러리](https://kiroween-2025.devpost.com/project-gallery)

주 타깃은 **Best Resurrection($5,000)**, 추가로 **Best Demo($1,000)**다. 종합상과 부문상은 중복 수상할 수 없고 보너스상은 별도 가능하다. Best Startup은 창업자 여부·LinkedIn·스타트업 웹사이트 자격을 확인하기 전에는 목표 상으로 확정하지 않는다. [공식 규정](https://kiroween.devpost.com/rules)

| 0:15–0:50 | Blackout 조명 선택과 결과 | 정보를 얻는 선택에 위험이 따른다 |
| 0:50–1:20 | Classic의 동일 입력 비교와 첫 차이 | 복원 과정의 실수를 찾아낸다 |
| 1:20–1:55 | Kiro 명세·실패·수정·재검증 기록 | Kiro가 실제 개발의 어디에 기여했는가 |
| 1:55–2:20 | 변경 규칙 카드와 다시 플레이 | 원본을 보존하면서 내 게임으로 바꾼다 |
| 2:20–2:40 | 사용 대상·한계·실제 링크 | 현재 가능한 것과 후속 계획 |

의도적 결함을 시연하면 `Demo mutation`으로 표시한다. REA 분석은 실제 성공한 근거만 Kiro 개발 과정 장면에 짧게 포함한다.

## 7. 일정: 결과물로 다음 단계 결정

기존 명세의 11/28 시험·시험 전 사용자 검토 주 1시간 제약을 유지한다. 에이전트 작업시간과 사용자 시간을 별도 기록한다. 아래 날짜는 KST이며 각 단계는 완료가 아닌 목표다.

| 단계 | 기간 | 결과물 | 통과 조건 / 실패 시 축소 |
|---|---|---|---|
| P0 기준 확보 | 11/14–15 | 출처 등록부, 원본 실행, REA 조사 1건, 화면 설계 | 원본 3회 재현. REA 장애는 별도 기록하고 reference 진행 |
| P1 세로 구현 | 11/16–18 | 원본→기록→TS→브라우저 한 경로 | 3개 시나리오 비교 + 실제 시작/종료. 실패하면 시각 효과 중단 |
| P2 제품 경험 | 11/19–22 | Classic 완결, Blackout 한 규칙, 90초 체험 | 사용자 5분 플레이 검토. 원본 호환과 변경 규칙 판정 분리 |

| P5 제출 준비 | 12/03–04 | 빌드, 영상, 영문 설명, 공개 후보 | 12/04 18:00 내부 목표. 외부 게시·제출은 별도 권한 범위 |

공식 마감은 **12/05 07:00 KST**다. 마감 이후 앱·저장소·영상·연결 자료를 결과 발표까지 동결한다. 후속 상품 개발은 별도 저장소의 복사본에서 진행하며 제출 URL이 바뀌지 않게 한다. [일정·규정](https://kiroween.devpost.com/rules)

### 사용자 시간 배분

시험 전에는 주 1회 최대 60분 안에서 5분 플레이와 결정 질문 최대 3개를 처리한다. 외부 테스터 섭외·영상 제작은 시험 전에 배정하지 않는다. 11/29–30 관찰 약 60분, 12/03–04 최종 검토·영상·게시·제출 약 3시간은 **추가로 필요한 시간의 추정치**이며 일정 확보를 가정하지 않는다. 확보가 어렵다면 에이전트가 가능한 자료 준비를 먼저 끝내고 남은 외부 작업을 명시한다. 공개/제출은 허가 범위에서 진행한다.

### 범위가 밀리면

1. REA 추가 provider·추가 게임·3D 엔진·에디터·결제는 즉시 제외한다.
2. 인터랙티브 비교 화면을 실제 검증 결과 카드 3종과 JSON 다운로드로 축소한다. 다음으로 배경·소리를 줄이고, 좁은 화면은 플레이만 우선한다. Classic + 조명 한 규칙 + 원본 자동 검증은 유지한다. 11/22에도 이 핵심이 불가능하면 게임 변형 없는 출품으로 조용히 바꾸지 않고 출품 방향을 재결정한다.
3. 원본 실행·독립 expected가 성립하지 않으면 ‘검증된 복원’ 출품안을 중단하고 사용자에게 범위 재결정 자료를 제시한다. 정답을 TS에서 만들어 통과시키지 않는다.
4. 수상 목적이라도 공개 허가와 실제 Kiro 사용 근거를 건너뛰지 않는다.

## 8. 상품화는 두 단계로

**우선 고객 가설:** 짧고 반복 가능한 추리·위험 선택 게임을 즐기는 PC 플레이어. 공개 데모에서 재도전 의향과 무엇 때문에 재미있었는지를 확인한다. 아직 지불 의사나 시장 수요는 검증되지 않았다.

| 시점 | 상품 | 다음 투자의 조건 |
|---|---|---|
| 해커톤 | 무료 브라우저 데모 + 공개 소스 | 3명 이상 관찰, 플레이 실패 지점·이해도·재도전 의향 기록 |
| 이후 4주 | 독창적 세계·맵·사운드의 작은 유료 패키지 후보 | 10명 테스트에서 반복 플레이 이유 확인, 권리 등록부 완성 |
| 수요 확인 뒤 | 권리 보유 개발자를 위한 복원·회귀 검증 서비스 | 실제 상담 3건과 유료 pilot 의향. 범용 자동 리메이크는 약속하지 않음 |

게임 판매와 B2B 복원 도구는 서로 다른 고객이다. 둘을 한 MVP에서 동시에 사업화하지 않는다. 오픈소스 제출 이후의 유료 배포 자체와, 이미 공개한 코드의 라이선스를 회수하는 것은 다른 문제다. 새 콘텐츠·패키지·지원의 가치로 판매하되 사용한 코드·자산의 조건을 유지한다. 판매 가격·Steam 일정·매출은 현재 확정하지 않는다.

## 9. 구현에 넘기는 첫 작업

1. Kiro에서 P0 요구사항과 수용 조건을 작성하고 실제 사용 근거를 저장한다. `.kiro/specs/classic-restoration/`, `.kiro/specs/blackout-variant/`에 작업을 연결하고, 공개 후보에서 `.kiro`가 무시되거나 빠지지 않았는지 확인한다.
2. reference 배포본·라이선스를 확인하고 고정 환경에서 반복 실행한다.
3. REA 실행 가능성을 제한된 조사로 확인하고 결과와 한계를 남긴다.
4. Classic 한 행동을 원본 기록과 비교한다.
5. 한 화면의 플레이를 만들고 그 뒤 Blackout 변형을 붙인다.
