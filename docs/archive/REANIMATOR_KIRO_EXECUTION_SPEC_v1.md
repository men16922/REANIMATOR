## 0. Kiro에게 주는 실행 지시

이 문서를 실행 가능한 제품을 만드는 작업 명세로 사용한다. 계획 문서만 다시 작성하고 끝내지 말고, 로컬에서 동작하는 MVP와 검증 결과, 제출 준비 자료까지 완성한다.

### 실행 원칙

1. 현재 저장소와 기존 사용자 지시, AGENTS.md, 기존 Kiro 설정을 먼저 읽는다. 사용자의 최신 지시와 실행 환경의 권한 규칙을 우선한다.
2. 비어 있는 작업 폴더라면 이 명세에 맞는 새 프로젝트를 구성한다. 기존 프로젝트가 있다면 관련 없는 파일이나 작업을 덮어쓰지 않는다.
3. 일반적인 기술 선택과 되돌릴 수 있는 로컬 구현은 스스로 진행한다. 작은 선택마다 사용자에게 확인을 요구하지 않는다.
4. 의존성 설치, 빌드, 로컬 실행, 디버깅, 테스트, 문서 작성은 해당 실행 환경이 허용하는 범위에서 진행한다.
5. 공개 저장소 생성, 원격 푸시, 실제 배포, 게시, 계정 로그인·크레딧 등록, Devpost 제출은 해당 세션에서 확인된 사용자 허가 범위를 따른다. 이 MD의 전달만으로 외부 작업 허가가 추가된 것으로 간주하지 않는다. 외부 작업이 남더라도 먼저 검토 가능한 로컬 결과물을 완성한다.
6. 실제 확인한 사실, 설계상의 가정, 계획한 목표를 구분한다. 실행하지 않은 테스트나 생성하지 않은 URL을 완료로 표시하지 않는다.
7. 각 Phase에서 구현·실행·검증을 마친 다음 다음 Phase로 진행한다. 발견한 오류를 그대로 둔 채 기능 수를 늘리지 않는다.
8. 작업을 중단하거나 다음 세션으로 넘길 때는 완료 범위, 실제 명령과 결과, 남은 문제, 다음 명령을 docs/PROGRESS.md에 기록한다.
9. 이 문서 안의 명령과 경로 중 아직 존재하지 않는 것은 구현할 계약이다. 이미 만들어져 있다고 가정하지 않는다.
10. 제품 UI와 제출용 README·설명·영상 대본은 영어를 기본으로 한다. 사용자에게 보고하는 진행 상황은 한국어로 작성해도 된다.

### 가장 먼저 할 일

- 기준 소스와 라이선스, 실제 실행 방법을 확인한다.
- 선정한 실행 환경에서 원본을 반복 실행한다.
- 원본의 관찰 결과를 TypeScript 구현과 비교할 최소 경로를 만든다.
- 이 경로가 성립한 다음 플레이 화면과 비교 화면을 확장한다.

라이선스나 실행 가능성을 확인할 수 없다면, 같은 upstream의 공식 저장소·배포본을 확인하고 이미 확인된 작업을 보존한다. LLM이 추측한 동작으로 기준 결과를 만들어 진행하지 않는다.

## 1. 제품의 목적과 출품 전략

### 한 문장 정의

REANIMATOR는 오래된 터미널 게임을 현대적인 브라우저에서 플레이하고, 복원 과정에서 바뀐 규칙을 기준 실행 기록과 비교해 찾아내는 앱이다.

### 대상 사용자

- 작은 레거시 게임을 현대 환경으로 옮기려는 개발자.
- 과거 소프트웨어의 규칙과 구현을 직접 체험하려는 학습자.
- 브라우저에서 고전 게임을 플레이하고 동작 원리를 살펴보려는 사용자.

이 대상은 제품 가설이다. 실제 사용자 채택·시장 수요·교육 효과를 검증했다고 표현하지 않는다.

### 해결하려는 문제

레거시 프로그램을 새 언어와 UI로 옮길 때 겉보기에는 잘 동작해도 입력 처리, 난수 소비, 규칙 적용 순서가 달라질 수 있다. REANIMATOR는 플레이 경험과 동작 비교를 연결하여, 무엇을 보존했고 어디에서 차이가 생겼는지 확인할 수 있게 한다.

### 이번 출품물의 정확한 범위

- 기준 게임 한 개.
- 고정된 reference 버전 한 개.
- 정해진 reference 실행 환경 한 개.
- 새 TypeScript 구현 한 개.
- 브라우저 플레이 화면과 비교 화면.
- 실제 reference 실행으로 생성한 시나리오별 기록.
- 발견한 차이와 수정 결과를 보여주는 검증 기록.

Kiro가 개발 과정에서 소스 분석·명세·복원을 지원한다. 사용자가 임의의 게임이나 바이너리를 올리면 자동으로 복원해주는 범용 서비스는 이번 제품의 약속에 포함하지 않는다.

### 공식 심사 기준을 제품에 연결하는 방법

2026-11-14에 확인한 공식 규칙은 다음 다섯 기준을 각각 20%로 평가한다.

| 기준 | 제품에서 보여줄 내용 |
| --- | --- |
| Potential Impact | 누구에게 어떤 복원·검증 문제를 해결하는지, 사용자가 실제로 무엇을 할 수 있는지 |
| Technological Implementation | Kiro의 Specs·Steering·Hooks가 구현과 오류 발견에 어떻게 기여했는지 |
| Design | 처음 방문해 플레이하고, 관심이 생기면 비교·검증으로 이동하는 완결된 흐름 |
| Innovation / Idea | 같은 입력에서 달라진 행동을 찾아내고 수정 후 재검증하는 경험 |
| Presentation | 작동하는 게임, 불일치 발견, 수정 결과를 연결한 짧은 시연 |

이 문서의 추천과 목표 수치는 자체 설계 판단이다. 공식 합격 기준이나 수상 확률을 의미하지 않는다.

## 2. 기준 게임과 출처를 고정한다

### 선정안

Hunt the Wumpus의 Eric S. Raymond 배포판 1.12를 비교 기준으로 사용한다.

공개 패키지 정보에서 확인한 내용:

- Homebrew 패키지명: wumpus
- 공식 패키지 페이지: https://formulae.brew.sh/formula/wumpus
- 해당 페이지의 라이선스 표기: BSD-2-Clause
- 해당 페이지의 안정 버전 표기: 1.12
- Apple Silicon용 패키지 지원이 안내되어 있다.
- 패키지 설명은 옛 BASIC Hunt the Wumpus의 동작을 재현한 구현이라고 소개한다.

원래 제안의 BASIC 게임 복원 방향을 실행 가능하게 구체화한 선택이다. 이번 비교의 기준은 선정한 C 배포본이다. 모든 역사적 Wumpus 변형과 같다고 표현하지 않는다.

### 원본 확인 위치

- 유지보수자 프로젝트 페이지: http://www.catb.org/~esr/wumpus/
- 공식 저장소: https://gitlab.com/esr/wumpus
- 배포 아카이브: http://www.catb.org/~esr/wumpus/wumpus-1.12.tar.gz
- 라이선스 원문 위치: http://www.catb.org/~esr/wumpus/COPYING
- README 위치: https://www.catb.org/~esr/wumpus/README.html
- Homebrew Formula: https://formulae.brew.sh/formula/wumpus

공식 사이트 접근이 불안정하면 연결된 upstream 저장소와 패키지 정보를 함께 사용한다. 최신 HEAD를 조용히 대신 사용하지 말고, 선택한 release 또는 commit을 명시한다.

### Phase 0에서 직접 확인할 사실

1. 다운로드한 소스의 실제 라이선스와 저작권 고지.
2. 선택한 파일이 1.12 배포판 또는 명시한 commit에 해당하는지.
3. 빌드와 실행 방법, seed 옵션, 입력·종료 동작.
4. 게임 규칙과 상태 변수의 의미.
5. C 난수 함수와 초기 배치·이동·사격에서 난수가 소비되는 시점.
6. 정상 행동, 잘못된 입력, 승리·패배, 재시작 질문의 실제 동작.

공개 소스 조사에서는 seed 옵션과 libc rand 사용이 확인되었다. 정확한 입력 프로토콜과 계측 위치는 구현 시 소스를 읽고 실행하여 확정한다.

### 출처와 파일 보존

- reference/upstream/에는 선택한 원본 소스를 수정 없이 보관한다.
- 계측을 위한 변경은 reference/patches/의 별도 패치로 관리한다.
- THIRD_PARTY_NOTICES.md에 upstream, 버전, 라이선스, 가져온 파일, 계측 범위를 기록한다.
- 원본의 저작권·라이선스 고지를 유지한다.
- 새 코드의 라이선스는 기존 자료와 양립하도록 정한다. 기본 제안은 새 코드 MIT, vendor 코드는 원래 고지 유지다.
- 아트·효과음은 직접 만들거나 사용 조건이 명확한 자료를 사용하고 출처를 기록한다.

### manifest에 남길 값

실제로 계산한 값만 저장한다.

- 기준 프로젝트 이름, upstream URL, release / commit.
- 다운로드 아카이브 SHA-256.
- 원본 핵심 소스 SHA-256.
- 계측 패치 SHA-256.
- 실행 환경과 컴파일러·libc 정보.
- 실행 환경을 container로 고정했다면 실제 image digest.
- 컴파일 명령과 옵션.
- trace schema version.
- 입력 시나리오와 expected trace 해시.

확인 전 값은 미확인으로 두고, 가짜 SHA나 image digest를 넣지 않는다.

## 3. 필수 제품 기능

### F1. 브라우저에서 바로 플레이

- 로그인 없이 새 게임을 시작한다.
- 이번 reference에서 확인한 이동, 사격, 위험 조우, 승리·패배 규칙을 구현한다.
- 남은 화살, 현재 위치, 사용 가능한 행동, 최근 메시지를 이해하기 쉽게 보여준다.
- 마우스와 키보드로 조작할 수 있게 한다.
- 브라우저 새로고침과 새 게임의 의미를 명확히 한다.
- 숨겨진 위험 위치를 일반 플레이 화면에 무조건 노출하지 않는다.
- 상태 계산과 UI를 분리한다. UI 애니메이션이 게임 난수나 규칙에 영향을 주지 않게 한다.

아이템 수집·인벤토리·레벨업은 이 reference에 확인된 규칙으로 가정하지 않는다.

### F2. 시나리오 재생과 비교

- 사용자가 준비된 시나리오 하나를 선택한다.
- 같은 논리적 행동과 reference에서 기록한 난수 입력으로 TypeScript 구현을 실행한다.
- 기준 실행 기록과 새 구현의 상태·이벤트를 단계별로 보여준다.
- 재생, 일시정지, 한 단계 이동, 처음부터 다시 실행을 제공한다.
- 최초로 차이가 발생한 행동과 관련 필드를 표시한다.
- 단순 출력 문구·색상·애니메이션 차이와 게임 규칙 차이를 구분한다.

기준 데이터가 저장된 trace라면 UI에 Reference execution recording이라고 표기한다. 기준 프로그램이 현재 브라우저 안에서 실행 중이라고 표현하지 않는다.

### F3. 검증 범위와 결과

- PASS, FAIL, ERROR, NOT RUN을 구분한다.
- 검증 대상 reference 버전과 시나리오 ID를 확인할 수 있게 한다.
- 실제 실행한 개수와 결과만 표시한다.
- 첫 불일치의 expected / actual, 행동 번호, 난수 소비 위치를 제공한다.
- 결과를 JSON으로 내려받을 수 있게 한다.
- 검증한 범위와 아직 지원하지 않는 범위를 명시한다.
- 일부 시나리오 통과를 전체 게임의 완전한 동등성으로 표현하지 않는다.

### F4. 수정 전후 설명

- 실제 개발 중 발견한 오류가 있다면 재현 입력, 최초 실패, 수정 사항, 재검증 결과를 연결한다.
- 실제 오류가 충분히 명확하지 않으면 별도 demo mutation으로 comparator의 검출 능력을 보여줄 수 있다.
- demo mutation은 의도적으로 삽입한 오류라고 표시한다.
- 의도적 결함을 실제 개발 중 발견한 버그처럼 설명하지 않는다.
- mutation 기능은 일반 플레이의 기본 동작을 변경하지 않는다.

### MVP의 크기

- 플레이 화면 1개와 비교 화면 1개를 중심으로 구성한다.
- reference 기반 시나리오 3개로 시작한다.
- 최종 목표는 의미가 서로 다른 reference 시나리오 약 10개다. 이 숫자는 구현 목표이며 완료 기록이 아니다.
- 핵심 흐름이 안정화되면 접근성·문구·작은 시각 효과를 다듬는다.
- 계정, 결제, 협업, 다중 게임 업로드, 범용 디컴파일러, 대규모 클라우드 인프라는 이번 MVP의 범위에 넣지 않는다.

## 4. 권장 구현 구조

### 기본 스택

- 웹: React + TypeScript + Vite.
- 상태 엔진: UI와 독립된 TypeScript 모듈.
- 시각화: HTML/CSS/SVG 중심의 작은 2D 동굴 UI.
- reference: 선택한 C 소스와 별도 계측 빌드.
- reference 실행·수집: Python 3 표준 라이브러리 기반 runner를 우선한다.
- 테스트: TypeScript 단위·통합 테스트, Playwright로 핵심 브라우저 흐름.
- 배포 산출물: 정적 웹 빌드를 기본으로 한다.
- 패키지 관리자: 기존 저장소 설정이 없으면 npm과 lockfile을 사용한다.

현재 환경의 지원 버전을 확인하고 실제 설치 버전을 기록한다. 이유 없이 의존성을 최신 버전으로 일괄 교체하지 않는다.

### 정적 웹을 기본으로 하는 이유

reference 프로그램은 개발·CI에서 실행하여 검증 가능한 기록을 만든다. 공개 앱은 그 기록과 현재 TypeScript 엔진을 비교한다. 이 구조는 심사위원의 접근을 쉽게 하고, 서버나 Kiro 개발 세션을 계속 실행해야 하는 부담을 줄인다.

### 주요 경로

| 경로 | 역할 |
| --- | --- |
| src/engine/ | 상태 전이, 게임 규칙, 난수 주입 인터페이스 |
| src/reference-contract/ | 행동·trace·상태 스키마와 검증 |
| src/comparison/ | expected / actual 비교와 첫 불일치 탐지 |
| src/ui/ | 플레이, 시나리오 재생, 결과 표시 |
| src/data/ 또는 public/data/ | 공개용 trace·시나리오·manifest |
| reference/upstream/ | 변경하지 않은 기준 소스 |
| reference/patches/ | 최소 계측 패치 |
| reference/fixtures/ | 실제 reference 실행으로 만든 expected |
| tools/reference/ | 빌드, 원본·계측본 실행, 기록 생성, 반복 검증 |
| tests/ | 엔진·비교기·통합·브라우저 테스트 |

불필요한 monorepo나 여러 서비스로 나누지 않는다. 경로는 이 책임을 유지하는 범위에서 조정할 수 있다.

## 5. reference와 비교기의 신뢰성을 먼저 만든다

### 5.1 원본과 계측본을 분리

계측은 관찰을 위한 최소 변경으로 한정한다.

허용하는 변경:

- 난수 반환값 기록.
- 원시 입력 소비 위치 기록.
- 검토된 행동 경계의 상태 스냅샷.
- 실행 메타데이터 출력.

게임 규칙, 조건식, 자료형, 입력 해석, 난수 호출 횟수를 편의상 변경하지 않는다. 원본에 있는 예외 동작을 고치고 싶다면 먼저 원래 동작으로 기록하고, 별도의 의도적 변경으로 관리한다.

trace는 stderr 또는 별도 파일 디스크립터에 출력한다. 게임의 stdout과 섞지 않는다.

### 5.2 계측이 동작을 바꾸지 않았는지 확인

같은 고정 실행 환경에서 원본과 계측본에 동일 seed·입력을 넣는다.

- 게임 stdout이 일치하는지 확인한다.
- 정상 종료 결과가 일치하는지 확인한다.
- 제한된 줄바꿈 정규화가 필요하면 그 규칙을 문서화한다.
- 숫자·문구·순서 같은 의미 있는 결과를 지우는 정규화를 사용하지 않는다.
- PTY를 사용하면 입력 echo와 게임 출력의 차이를 구분한다.

이 확인을 통과한 계측본의 기록만 expected로 사용한다.

### 5.3 난수는 같은 seed만으로 맞추지 않는다

C의 libc rand와 TypeScript 난수 생성기가 같은 seed에서 같은 결과를 낸다고 가정하지 않는다.

검증 모드의 계약:

1. 초기 배치 이전의 첫 호출부터 마지막 호출까지 reference의 raw 난수 반환값을 기록한다.
2. 호출 순서, raw 값, 가능한 호출 위치 식별자를 남긴다.
3. TypeScript 검증 실행은 그 난수 테이프를 처음부터 소비한다.
4. reference의 나머지 연산·정수 변환 등 실제 규칙을 확인하여 동일하게 적용한다.
5. UI 효과용 난수는 게임 난수와 분리한다.
6. 유효성이 확인된 reference 기록에 대해 TypeScript가 난수를 더 소비하거나 다른 순서로 소비하면 구현 차이인 FAIL로 표시한다. 최초 소비 차이와 관련 행동을 남긴다.
7. fixture 손상·기록 누락·스키마 오류로 테이프 자체를 신뢰할 수 없으면 ERROR로 표시한다. 원인을 구분하지 못한 경우도 ERROR로 남기고 조사한다.
8. 부족한 테이프를 Math.random으로 보충하거나 마지막 값으로 채우지 않는다.

일반 자유 플레이에는 별도의 재현 가능한 난수 공급자를 사용할 수 있다. 이때 같은 seed가 reference와 동일한 플레이를 보장한다고 설명하지 않는다.

### 5.4 원시 입력과 논리적 행동을 구분

입력 한 줄이 게임 한 턴이라고 가정하지 않는다.

- inputIndex: reference runner가 전달한 원시 입력의 순서.
- actionIndex: 하나의 논리적 게임 행동이 완료된 순서.
- phase: 초기화, 입력 대기, 행동 완료, 게임 종료 등 관찰 단계.
- sequence: trace 이벤트 전체의 순서.

시작 안내, 행동 선택, 이동할 방, 사격 경로, 잘못된 입력 재질문, 재시작 질문을 소스와 실제 실행에서 확인한 뒤 매핑한다.

이번 MVP의 동등성 검증 대상은 정규화한 행동 이후의 게임 규칙과 상태 전이다. C의 원시 텍스트 파서를 TypeScript로 완전히 복제하는 기능은 포함하지 않는다. reference runner는 원래 입력 프로토콜을 사용하고, 새 UI는 버튼과 구조화된 행동으로 입력한다. 잘못된 원시 입력 처리는 reference runner의 검증, 잘못된 논리적 행동 처리는 TypeScript 엔진의 검증으로 나눠 기록한다.

### 5.5 비교할 상태는 명시적으로 정의

초기 후보 필드:

- 플레이어 위치.
- Wumpus 위치.
- 위험 방 위치.
- 남은 화살.
- 게임의 진행 / 승리 / 패배 상태.
- 논리적 행동 번호.
- 난수 소비 위치.
- 해당 행동에서 발생한 의미 있는 이벤트.

필드의 의미와 스냅샷 시점을 reference 코드에서 확인한 뒤 확정한다. 임시 변수까지 무조건 비교하지 않는다. 비교기에서 필요한 전체 상태와 일반 플레이 사용자에게 공개할 상태를 분리한다.

### 5.6 expected는 독립적인 reference에서만 생성

- expected trace 생성자는 reference runner 하나다.
- TypeScript 엔진의 입력은 논리적 행동, 명시적인 시작 조건, 난수 테이프뿐이다. 엔진은 expected 상태·다음 상태·정답 이벤트에 접근하지 않는다.
- expected 상태는 비교기만 읽는다. runner는 엔진이 계산한 actual을 비교기에 전달한다. expected에서 상태를 복사해 actual을 만드는 경로를 만들지 않는다.
- 초기화까지 검증하는 대표 시나리오는 TypeScript가 초기화 난수 테이프를 소비하여 초기 상태를 직접 계산해야 한다. 기준 스냅샷에서 시작하는 보조 시나리오가 있다면 그 이후의 상태 전이만 검증한다고 별도로 표시한다.
- TypeScript 실행 결과를 expected로 복사하는 자동 갱신은 금지한다.
- LLM이 계산한 값을 실제 reference 실행값처럼 저장하지 않는다.
- expected 변경은 reference 버전 변경, 계측 오류 수정 등 이유와 원본 실행 근거를 남긴다.
- CI와 일반 테스트는 expected를 조용히 다시 생성하지 않는다.
- reference와 새 엔진이 공유하는 것은 데이터 계약이다. 새 엔진의 규칙 로직으로 reference 결과를 재계산하지 않는다.

### 5.7 게임 결과와 runner 오류를 구분

| 상황 | 판정 |
| --- | --- |
| reference와 actual의 정의된 상태·이벤트가 일치 | PASS |
| 같은 조건에서 의미 있는 상태·규칙 결과가 다르거나, 유효한 기준 기록에 대해 엔진의 난수 소비가 다름 | FAIL |
| timeout, 입력 소진, fixture 손상·기록 누락, trace 파싱 실패, 빌드·프로세스 오류 | ERROR |
| 실행하지 않았거나 필요한 기준 기록이 없음 | NOT RUN |

게임의 패배 자체는 FAIL이 아니다. 양쪽 모두 같은 패배 결과라면 PASS가 될 수 있다. 프로세스의 실패를 게임의 패배로 바꾸지 않는다.

### 5.8 최소 데이터 계약

구체적인 TypeScript 타입과 JSON Schema 또는 동등한 런타임 검증은 구현 중 정의한다. 최소 계약은 다음과 같다.

Scenario:

- schemaVersion, id, title, purpose.
- referenceId와 source manifest 연결.
- seed 및 고정 실행 환경 식별.
- rawInputs: reference의 실제 입력 프로토콜.
- actions: 정규화된 게임 행동.
- expected trace 경로와 해시.
- 검증 범위 및 알려진 한계.

ReferenceTrace:

- 실행한 버전·환경·명령·입력 해시.
- raw random tape.
- phase / inputIndex / actionIndex / sequence를 가진 이벤트.
- 안정된 행동 경계의 정규화 상태.
- 게임 종료 결과.
- 프로세스 종료·오류 정보.

ComparisonResult:

- scenarioId, referenceId, appRevision.
- status: PASS / FAIL / ERROR / NOT RUN.
- comparedActions와 관찰 범위.
- firstDifference: 행동, 필드, expected, actual.
- reference / actual 난수 소비 위치.
- 실제 실행 시각과 실행 명령 또는 UI 동작.
- 오류가 있다면 구체적인 errorType과 메시지.

생성 시각처럼 실행마다 달라지는 메타데이터는 재현성 비교 대상에서 명시적으로 제외한다. 결정적 의미 데이터는 반복 실행 시 같아야 한다.

## 6. 사용자 경험과 시각 방향

### 첫 화면

- 제목과 한 문장 가치 설명.
- Play와 Inspect a replay 두 진입점.
- 첫 클릭으로 플레이 또는 준비된 시나리오가 열린다.
- 개발 도구 설정과 빌드 로그는 첫 화면을 차지하지 않는다.
- reference 버전·출처·검증 한계는 About / Evidence 영역에서 볼 수 있게 한다.

### 플레이 화면

- 읽기 쉬운 동굴·방 표현.
- 이동 가능한 선택지와 현재 행동 상태.
- 위험 힌트, 사격 입력, 남은 화살.
- 최근 메시지와 새 게임.
- 키보드 포커스와 명확한 버튼 상태.
- 좁은 화면에서도 핵심 행동이 가능하도록 구성.

### 비교 화면

- 시나리오 선택.
- 기준 실행 기록과 현재 복원본의 상태.
- 행동 타임라인과 한 단계 이동.
- 첫 불일치 강조.
- expected / actual 필드.
- 검증 결과 다운로드.
- trace가 사전 기록인지 현재 실행 결과인지 명확한 표시.

### 시각 스타일

어두운 동굴, 터미널의 녹색 또는 호박색 포인트, 절제된 레트로 분위기를 사용한다. 텍스트 대비와 조작 가능성을 우선한다. 화면 흔들림·깜빡임·음향은 핵심 정보 전달을 방해하지 않게 하고, 움직임 감소 설정을 존중한다.

새로운 그래픽은 CSS/SVG로 직접 제작하는 방식을 우선한다. 특정 상용 게임의 캐릭터·그래픽·음악을 전제로 하지 않는다.

## 7. Kiro를 실제 개발 과정에 사용한다

공식 요건은 Kiro를 이용해 작동하는 앱을 개발하고 그 사용을 설명하는 것이다. 확인한 규칙에는 앱 런타임에서 LLM이나 Kiro 호출을 필수로 넣으라는 조건이 없다. 이 해석을 기준으로 Kiro는 개발·검증에 활용하고, 공개 플레이와 비교는 결정적으로 동작하게 만든다.

### Specs

다음 기능 명세를 Kiro의 실제 spec 흐름으로 만든다.

1. reference execution and provenance.
2. deterministic game engine.
3. replay comparison.
4. playable interface.
5. release evidence and submission preparation.

각 명세는 요구사항, 수용 조건, 설계, 구체적인 작업을 포함한다. 작은 작업을 과도하게 여러 spec으로 쪼개지 않는다.

### Steering

최소한 아래 원칙을 프로젝트 지침에 반영한다.

- 검증 모드의 규칙과 난수 소비는 reference를 따른다.
- 의도적 UX 개선과 원본 호환성 검증을 구분한다.
- expected 생성은 reference runner의 책임이다.
- 실제 실행 결과만 성과로 기록한다.
- P0 범위를 우선한다.
- 사용자 화면은 영어, 문구는 짧고 구체적으로 작성한다.
- 출처와 라이선스 고지를 유지한다.
- 공개 코드·문서에 비밀값을 넣지 않는다.

### Hooks

설치된 Kiro 버전의 현재 hook 문서와 설정 형식을 확인한 뒤 실제 동작하는 구성을 만든다.

권장 사용:

- 엔진 또는 비교기 변경 후 관련 단위 테스트 실행.
- reference adapter 또는 schema 변경 후 관련 회귀 테스트 실행.
- 작업 완료 시 typecheck와 변경 범위 검증 실행.

가벼운 검증을 기본으로 하고, 매 파일 변경마다 전체 reference 빌드와 브라우저 테스트가 반복되는 구성은 피한다. 예상 결과 파일을 자동으로 덮어쓰는 hook은 만들지 않는다.

### Bugfix 기록

실제 실패 한 건에 대해 다음 연결을 남긴다.

- failing scenario.
- 원인.
- Kiro에 제공한 요구사항 또는 수정 지시.
- 수정한 코드.
- 실제 재검증.
- 남은 한계.

사용하지 않은 MCP·Crew·Powers를 사용한 것처럼 작성하지 않는다. 기본 범위는 Specs·Steering·Hooks로 충분하며, 반복 작업에 실제 가치가 확인되는 경우에만 추가 도구를 검토한다.

### Kiro 사용 기록

docs/KIRO_USAGE.md에 작업별로 다음을 기록한다.

- 실제 사용한 Kiro 기능과 실행 환경.
- 실제 Kiro 환경·버전과 대표 실행 근거. 설정 파일의 존재만으로 사용을 증명하지 않는다.
- 해당 기능이 해결한 작업.
- 생성하거나 변경한 파일.
- 사람이 내린 결정과 검토한 부분.
- 실패와 수정의 근거.
- 측정했다면 실제 시간·사용량, 측정하지 않았다면 미측정 표시.

원문 대화 전체를 공개할 필요는 없다. 비밀값과 개인 정보가 없는 대표 기록, 설정, 산출물, commit으로 설명한다.

현재 작업이 실제 Kiro에서 수행됐는지 확인할 수 없으면 Kiro usage: NOT VERIFIED로 유지한다. 로컬 구현은 진행할 수 있지만, Kiro 사용 요건까지 충족한 제출 준비 완료로 보고하지 않는다.

## 8. 구현 단계와 통과 조건

### Phase 0 — 기준 실행과 위험 확인

목표: 원본이 실제로 실행되고, 같은 조건에서 재현되는지 확인한다.

작업:

- 작업 폴더·기존 설정 확인.
- 실제 Kiro 실행 환경·버전과 대표 작업 기록 확인. 확인되지 않으면 사용 상태를 NOT VERIFIED로 유지.
- 기준 소스와 라이선스 고정.
- 원본 빌드와 실행.
- 입력·종료·난수·상태 경계 조사.
- 작은 시나리오 3개 확보.
- 실행 환경과 해시 기록.

통과 조건:

- 원본 실행 명령과 실제 출력이 있다.
- 같은 환경·seed·입력에서 결정적인 결과가 재현된다.
- 다음 단계에서 무엇을 계측할지 소스 위치와 이유가 정리돼 있다.

첫 기술 검증은 에이전트가 실제로 작업하는 약 2시간을 초기 예산으로 잡는다. 이는 사용자의 직접 작업시간이나 구현 시간 보장이 아니다. 사용자의 검토·실행 보조가 얼마나 필요했는지 별도로 기록한다. 막히면 현재 대상에서 가장 작은 정상 시나리오까지 범위를 줄이고, 실행 실패를 기록한다. UI 작업으로 문제를 가리지 않는다.

### Phase 1 — 신뢰할 수 있는 trace와 첫 비교

작업:

- 원본을 보존한 별도 계측 패치.
- stdout과 trace 출력 분리.
- 원본 / 계측본의 출력·종료 일치 확인.
- 초기화부터 난수 테이프 기록.
- 행동 경계의 상태와 입력 매핑.
- TypeScript 상태 전이 최소 구현.
- 첫 expected / actual 비교.

통과 조건:

- 세 시나리오에서 원본과 계측본의 관찰 가능한 결과가 일치한다.
- 반복 생성한 trace의 의미 데이터가 일치한다.
- TypeScript의 실제 행동 결과 한 개 이상을 비교한다.
- 의도적 테스트 차이를 comparator가 정확히 검출한다.
- timeout·입력 소진·테이프 부족을 PASS로 처리하지 않는다. 유효 fixture에 대한 엔진 소비 차이와 fixture 자체의 손상을 각각 FAIL과 ERROR로 구분한다.

### Phase 2 — 플레이 가능한 게임

작업:

- reference에서 확인한 필수 게임 규칙 구현.
- 게임 엔진과 UI 분리.
- 자유 플레이용 난수 공급자와 검증용 tape 공급자 분리.
- 이동·사격·위험·승패 UX 구현.
- 기본 조작·접근성·좁은 화면 확인.

통과 조건:

- 사용자가 시작부터 종료까지 게임을 플레이한다.
- 새 게임이 이전 상태를 잘못 재사용하지 않는다.
- UI 동작이 검증 엔진을 우회하지 않는다.
- unsupported 상태를 조용히 정상 처리하지 않는다.

### Phase 3 — 비교와 증거 화면

작업:

- 시나리오 선택과 단계별 재생.
- expected / actual 비교.
- 첫 불일치 탐지·표시.
- FAIL / ERROR 구분.
- 결과 JSON 내보내기.
- 출처·버전·검증 범위 표시.
- 실제 수정 사례 또는 표시된 demo mutation 연결.

통과 조건:

- 같은 시나리오를 반복 실행해 같은 의미 결과를 얻는다.
- 잘못된 actual의 최초 불일치를 정확히 표시한다.
- reference recording과 현재 actual 실행의 구분이 명확하다.
- 다운로드 결과와 화면의 결과가 일치한다.

### Phase 4 — 검증 확대와 제품 정리

작업:

- 서로 다른 규칙을 검증하는 reference 시나리오를 약 10개까지 확대.
- 초기 구현에 사용하지 않은 추가 시나리오를 생성해 확인.
- 핵심 브라우저 흐름 검증.
- 영어 문구·읽기 쉬운 UI·키보드 동작 정리.
- 첫 사용자 관점의 실행 안내 확인.

추가 시나리오를 실제로 나중에 만들었다면 그 생성 시점과 사용 이력을 남긴다. 이름만 holdout으로 붙여 독립 평가라고 주장하지 않는다.

### Phase 5 — 제출 가능한 패키지

작업:

- 깨끗한 checkout 또는 동등한 격리 환경에서 문서의 설치·빌드·테스트 명령 확인.
- 정적 웹 빌드.
- 영어 README와 실행·reference 재생성 안내.
- 영어 Devpost 설명 초안.
- 2분 40초 안팎의 영상 대본과 촬영 순서.
- Kiro 사용 기록과 실제 평가 결과.
- 배포·공개·제출에 남은 작업 표시.

통과 조건:

- 사용자가 다음 세션에서 실행 가능한 상태다.
- 준비 완료와 실제 공개·제출 완료를 구분한다.
- 실제 URL이 없으면 Pending publication으로 둔다.
- 외부 작업에 필요한 허가가 없더라도 로컬 구현과 준비 자료는 완성한다.

## 9. 필요한 테스트

### reference 무결성과 재현성

- source / patch / fixture hash 확인.
- 원본과 계측본의 출력·정상 종료 일치.
- 동일한 입력과 환경의 반복 실행 일치.
- 초기화 난수가 누락되지 않는지 확인.
- trace 스키마와 원시 입력 매핑 검증.

### 게임 엔진

소스에서 실제 규칙을 확인하여 다음 범주를 작성한다.

- 정상 이동과 유효하지 않은 이동.
- 사격과 남은 화살 처리.
- 위험 조우.
- 승리와 패배.
- 종료 후 행동 처리.
- 재시작 또는 새 게임.
- 잘못된 논리적 행동에 대한 엔진 계약과 reference의 입력 재질문에 대응하는 UI 계약. 원시 텍스트 파서의 전체 호환성은 별도 주장하지 않는다.

임의로 기대하는 현대 게임 규칙을 reference의 규칙으로 사용하지 않는다.

### 비교기

- 완전히 같은 trace.
- 첫 행동부터 다른 trace.
- 뒤쪽 행동에서 처음 달라지는 trace.
- 길이가 다른 trace.
- 필수 필드 누락.
- 유효 fixture에서 엔진이 난수를 과다·오순서 소비하는 FAIL.
- fixture 손상·기록 누락으로 tape를 신뢰할 수 없는 ERROR.
- raw 출력 차이와 의미 상태 차이의 구분.
- runner 오류가 PASS 또는 게임 패배로 바뀌지 않는지 확인.

### 브라우저 핵심 흐름

1. 첫 방문에서 게임 시작.
2. 행동 입력과 상태 갱신.
3. 새 게임.
4. 시나리오 선택과 단계별 재생.
5. 비교 결과와 첫 불일치 확인.
6. JSON 내보내기.
7. 키보드 조작과 좁은 화면.
8. source / evidence 정보 열람.

### 평가 결과 기록

docs/EVALUATION.md에는 실제 실행한 내용만 넣는다.

- 실행 시각, app revision, reference version.
- 실행 환경.
- 사용한 명령.
- 시나리오 ID와 입력 출처.
- PASS / FAIL / ERROR / NOT RUN 집계.
- 발견한 문제와 수정 전후.
- 비교한 필드와 제외한 필드.
- 아직 검증하지 않은 규칙·경로.

개발 중 발견한 오류와 인위적인 comparator 테스트를 구분한다. 실제 측정 전에는 통과율, 성능 향상, 개발 시간 절감 수치를 만들지 않는다.

## 10. 개발 명령과 실행 문서

아래 기능을 npm scripts 또는 명확한 동등 명령으로 제공한다. 명령 이름은 구현 계약이며 아직 존재한다고 가정하지 않는다.

| 명령 | 목적 |
| --- | --- |
| npm run dev | 로컬 웹 앱 실행 |
| npm run typecheck | TypeScript 검사 |
| npm test | 엔진·schema·비교기 테스트 |
| npm run test:e2e | 브라우저 핵심 흐름 |
| npm run build | 정적 산출물 생성 |
| npm run reference:build | 고정된 reference 원본·계측본 빌드 |
| npm run reference:verify | 원본·계측본·재현성 검증 |
| npm run reference:capture | 명시적으로 expected 후보 기록 생성 |
| npm run verify | release에 필요한 검사 집계 |

reference:capture는 일반 테스트나 UI 실행의 부수 효과로 동작하지 않게 한다. 기존 expected를 바꾸려면 새 기록과 변경 이유를 확인할 수 있어야 한다.

README에는 다음 두 경로를 구분한다.

- 앱을 바로 실행하는 경로: 준비된 reference 기록으로 플레이·비교.
- reference를 직접 재현하는 경로: 필요한 C 도구·환경을 준비하여 원본 실행과 기록 생성을 확인.

브라우저 사용자에게 C 컴파일 환경 설치를 요구하지 않는다.

| 1:25–1:55 | Kiro 명세·hook·수정 근거를 실제 파일과 결과로 짧게 설명 |
| 1:55–2:20 | 수정 후 재검증과 결과 내려받기 |
| 2:20–2:40 | 검증 범위·한계·실행 위치 정리 |

불일치 예시가 의도적인 mutation이면 화면과 설명에 그 사실을 표시한다. 영상에 나온 동작은 실제 빌드에서 재현 가능해야 한다.

### 심사 기간 접근

공식 규칙상 심사위원의 무료 테스트 접근은 심사 종료까지 제공해야 한다. 확인한 종료 시점은 2027-01-30 06:00 KST이다.

정적 앱과 재현 가능한 기록을 제공하여 개발용 크레딧·개발 세션의 수명과 분리한다. 최종 공개 전에 공식 일정 변경 여부를 다시 확인한다.

### 추가 게시물

앱과 필수 자료가 완성되면 개발 기록으로 블로그 초안을 만들 수 있다. 실제 게시 여부는 사용자 허가를 따른다. 보너스상을 위해 별도 제품을 추가하지 않는다.
