# Abuse 복원·재해석 검증 계약 v3

2026-11-14 · 구현 전 계약 · 실제 통과 결과가 아님

## 1. 검증 단위

전체 Abuse 복원이 아니라 명시한 행동·상태·구간의 복원을 검증한다. 원본 EXE가 최종 비교 기준이며 공개 소스와 현대 포트는 보조 근거다. 공개 소스가 있음을 밝히고 블라인드 분석으로 소개하지 않는다.

| 근거 유형 | 예시 | 증명하지 못하는 것 |
|---|---|---|
| `binary-static` | EXE 해시·loader·함수 주소·명령·참조 | 실제 실행 경로와 타이밍 전체 |
| `runtime-observed` | 원본 캡처·입력·디버거 상태 | 관찰하지 않은 분기 |
| `script-read` | 실제 배포본 Lisp 파일과 위치 | 바이너리에서 독립 복원했다는 주장 |
| `source-crosscheck` | 공개 소스 revision·파일·줄 | 원본 EXE와 해당 소스의 완전 일치 |
| `inferred` | 후보 상태/함수 의미 | 확인된 사실 |
| `new-design` | 새 조명·맵·게임 목표 | 원작 호환성 |

`BEHAVIOR_MAP.md`의 열: behaviorId, 원본 해시, 코드/데이터 영역, 주소 체계, 함수/명령, 정적 근거, 실행 관찰, 스크립트/소스 참조, 확신 수준, 미관찰 경로, 구현 파일, scenarioId.

## 2. 원본과 변환본

원본 패키지·실행 파일은 변경하지 않는다. 실행 작업 복사본, 압축 해제/메모리 덤프, 분석 프로젝트, 계측본은 별도 저장한다. 변환 도구·버전·명령·원본/변환 SHA-256·매핑을 기록한다.

DOS stub와 본체를 구분하고 파일 오프셋·정적 로드 주소·실행 세그먼트 주소를 혼용하지 않는다. 변환본 코드가 원본의 어느 영역인지 설명되지 않으면 원본 분석으로 판정하지 않는다. 유효한 도구 지원 없이 raw 데이터를 임의 ISA로 해석해 성공 처리하지 않는다.

계측·중단점·frame-step이 타이밍에 영향을 줄 수 있다. 비계측 관찰과 비교하고 영향·범위를 남긴다. 소스 계측 빌드의 결과는 원본 EXE와 관계를 확인하기 전 보조 근거로만 쓴다.

## 3. 재현 조건

시나리오마다 원본 EXE/데이터 해시, emulator/version/config, 초기 저장 상태·맵·위치·속도·체력, 입력 시점/유지 시간, 키/마우스 좌표계, simulation tick과 영상 frame 매핑을 기록한다.

수동 3회 플레이는 실행 가능성 관찰이다. 결정적 입력 replay나 동일 상태 trace를 증명하지 않는다. G1에서 입력 주입·상태 복원 가능성을 먼저 실측한다.

실제 RNG 알고리즘·상태·소비 순서를 확인한 범위에서만 재현한다. 같은 seed만으로 동일성을 주장하지 않는다. 난수를 관찰할 수 없으면 우선 난수에 영향받지 않는 이동/충돌을 비교하고 RNG 관련 경로는 NOT RUN으로 남긴다. 부족한 난수 기록을 새 엔진 난수로 채우지 않는다.

## 4. 두 수준의 비교

| 수준 | 필요한 증거 | 허용 판정 |
|---|---|---|
| 상태 비교 | 관찰된 상태 변수 의미·tick·동일 초기 조건·입력 | 선언한 필드의 정확한 일치 |
| 관찰 비교 | 원본 프레임·측정 좌표·입력 시점·오차 범위 | 해당 관찰값의 허용 오차 내 일치 |

상태가 보이지 않으면 영상만으로 내부 속도·난수·체력 전체가 같다고 주장하지 않는다. 관찰 비교는 G1에서 반복 측정 오차를 산정해 허용 오차를 미리 고정한다. FAIL 뒤 통과를 위해 임계값을 넓히지 않는다. 화면상 위치와 월드 좌표를 구분하고 카메라·스프라이트 기준점을 고정한다.

시나리오가 다른 맵/지형을 쓰면 대응 지형·초기 상태를 명시하고 그 기하 조건에서의 행동만 비교한다. 원본 맵 전체 복원으로 확대하지 않는다.

## 5. 독립 expected

- expected는 원본 실행에서 얻은 기록만 사용한다. 새 TS 엔진이나 LLM이 계산한 정답을 reference로 저장하지 않는다.
- 엔진 입력은 시작 상태·입력·검증된 시간/난수 계약이다. 엔진은 expected의 다음 상태를 읽지 않는다.
- 비교기만 expected와 actual을 함께 읽는다. 공통 엔진 함수를 정답 오라클로 사용하지 않는다.
- 초기 스냅샷을 넣었다면 그 이후 전이만 검증한 것으로 표시한다.
- expected 변경은 원본 재캡처·측정 오류 수정 등 이유와 증거를 남긴다. 일반 gate와 hook은 이를 갱신하지 않는다.
- 최소 1개 새로운 입력/지형 사례를 구현에 사용하지 않고 holdout으로 보존한다. holdout을 보고 수정했으면 개발 사례로 이동하고 새 사례를 확보한다.

## 6. 최소 시나리오

| ID | 조사할 동작 | 결과 필드 후보 |
|---|---|---|
| M01 | 평지 이동 후 키 해제 | 위치·정지 시점 |
| M02 | 점프와 착지 | 높이·궤적·착지 시점 |
| M03 | 벽으로 이동 | 접촉 위치·관통 여부 |
| M04 | 다른 유지 시간/장애물의 holdout | M01/M03과 같은 판정 |
| C01 | 고정 조준·단발 사격 | 생성 시점·방향·발사 간격 |
| C02 | 고정 조건 피격 | 충돌 사건·체력 변화 |

필드는 실제 관찰 가능성을 확인한 뒤 확정한다. M01/M03을 우선하며 G2는 3개 이상 시나리오와 핵심 행동 2개 이상을 요구한다. 사격·피격은 G3에서 가능 범위를 정한다. 검사 수가 재미나 전체 호환성의 증거는 아니다.

## 7. 결과 분류

- PASS: 유효한 원본 근거와 같은 비교 조건에서 선언 필드/오차 계약 충족.
- FAIL: 유효한 기준·동일 조건인데 선언한 동작/필드/오차 불일치.
- ERROR: 실행 실패·timeout·손상·누락·주소 매핑 실패·측정 불가 등으로 판정 불능.
- NOT RUN: 미실행 또는 필요한 원본 근거가 아직 없음.

필수 시나리오 ERROR/NOT RUN도 release gate를 통과하지 못한다. 게임 패배는 검사 FAIL과 다르다. 빈 fixture 집합은 PASS가 아니다.

결과 필드: scenarioId, referenceId/hash, appRevision 또는 작업 파일 manifest, toolVersions, initialStateId, inputHash, validationKind, measuredFields, excludedFields, toleranceContract, status, firstDifference, rawEvidencePaths, knownLimits.

## 8. 재해석 규칙

`validationKind`는 `reference-state`, `reference-observation`, `variant-contract`로 나누고 집계를 합치지 않는다. 새 조명/맵/목표는 variant-contract다.

조명 검사: 켜짐/꺼짐, 배터리 0/최대, 재점등 조건, pause, restart, 탭 포커스 상실. 규칙 밖의 이동·충돌·탄약 변화는 허용하지 않는다. 조명 분기 이후 세션을 원본 전체 trace와 동등하다고 하지 않는다.

## 9. 비교기·브라우저 확인

같은 actual의 PASS, 실제 불일치의 첫 차이, 길이 차이, 누락 필드, 손상 fixture, 미실행을 검사한다. 고의 변조 actual은 comparator 테스트이며 원본에서 발견한 버그가 아니다.

브라우저: 첫 시작, 키/마우스, pause/resume, 포커스 상실 시 입력 해제, 사망/탈출, restart 상태 초기화, 음량, 실제 근거 링크, recorded/live 표기를 확인한다. E2E 자동화 외에 사람이 화면·소리·재미를 확인한다.

`docs/EVALUATION.md`에 명령·환경·실제 결과·한계만 기록한다. 공개 빌드에서는 private 원본/미검토 자료 제외와 출처 고지를 별도 확인한다.
